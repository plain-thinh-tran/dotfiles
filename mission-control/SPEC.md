# Mission Control

Local web app for deciding what multi agent skill runs (`/avengers`, `/prod-ready-check`) need from Thinh, and sending the decisions back to the Conductor session that asked. Conductor stays the place where work happens; this app is where decisions happen.

## Stack

- Bun 1.4 (`/opt/homebrew/bin/bun`), `Bun.serve` with HTML imports (`import index from '../web/index.html'`), React 19 + react-dom, TypeScript, plain CSS. No other runtime deps.
- Port 4747 on 127.0.0.1. Live updates over SSE.
- Shared types in `src/types.ts`; do not change their shape without updating this spec.

## Data

- `MC_HOME` env, default `~/.mission-control`. Run files at `$MC_HOME/runs/<runId>.json`, shape `Run` from `src/types.ts`.
- All writes are atomic: write `<file>.tmp-<pid>` then `rename`.
- Every read-modify-write of a run file (server and CLI) runs inside `withRunLock(runId, fn)` in `src/store.ts`: create `<run>.lock` with `openSync(path, 'wx')`, retry every 25ms for up to 5s, break a lock whose mtime is older than 10s, always remove it in `finally`.
- Agents never write run files directly; they go through the `mc` CLI. The app writes only answer, state, submission fields.
- Archived thread ids live in `$MC_HOME/archived.json` (an array of sessionIds, written atomically under a lock). Prune on server start deletes only the run files of archived threads whose runs were all last updated more than 14 days ago (and drops those ids from `archived.json`). Nothing else is ever deleted automatically.
- Custom thread names live in `$MC_HOME/names.json` (`{ [sessionId]: string }`, written atomically under a lock, at most 120 characters, trimmed; an empty or null name removes the entry and returns the thread to its automatic name).
- Never write to Conductor's DB.

## Threads

- One thread per `session.conductorSessionId`, built from all runs with that session. Threads never disappear on their own: a thread stays in the list whatever its runs' status (`mc done` hides nothing). Thinh archives a thread himself (`Thread.archived`); archived threads are hidden unless requested, and then listed below the active ones.
- Threads from steps: a session whose steps file (`$MC_HOME/steps/<sessionId>.json`) has a `current` step gets a thread even when it has no runs. Its session info comes from the Conductor DB lookup (`displayName` by the usual rule, `description` = `sessions.title`, workspace path, directory name, repo and branch from `workspaces` / `repos`; the session id stands in for the name when the DB has no row), live state as usual, `runs: []`, counts 0, `updatedAt` by the same max rule, and `agents` taken from the agents seen in the step history (a step without an agent counts as the orchestrator). When `current` is cleared (`mc step --clear`) and there are still no runs, the thread disappears (nothing was ever asked; this is not auto archiving). Archived session ids still hide it. When the first run arrives for the session it simply becomes a normal thread with the same sessionId.
- `agents`: union of all runs' agents deduped by `id`, orchestrator first.
- Within a run, todos are ordered `needs-you` first, then `key-decision`, keeping the original order otherwise.
- Grouped: "Needs you" (open or ready to submit items, or waiting on Thinh), then "Working" (agent busy, nothing for Thinh), then "Idle" (collapsible, remembered in localStorage `mc-idle-open`), then "Archived"; newest `updatedAt` first inside each group. Logic in `src/threadGroups.ts`.

### Live state

Computed every 3 seconds and broadcast when changed.

1. Conductor DB, read only: `~/Library/Application Support/com.conductor.app/conductor.db`, open with `new Database(path, { readonly: true })` from `bun:sqlite`. Query `select id, status from sessions where id in (...)`. Values seen: `working`, `waiting`, `idle`, `error`. If the DB cannot be opened, skip it. `MC_CONDUCTOR_DB` overrides the path (used by tests with a copy).
2. Processes: `ps -axo pid=,command=`. A session is alive when some process whose command contains `/claude` (the claude CLI or `claude-rc`) has cwd equal to `session.workspacePath`. Get cwds with one call: `lsof -a -d cwd -p <pid,pid,...> -Fpn`.
3. A wait is pending when a process command contains `mc wait <runId>` (or `mc.ts wait <runId>`) for a run in the thread.

Thread naming comes from the same Conductor DB: `select s.id, s.status, s.title, w.workspace_name, w.user_set_workspace_name, w.pr_title, w.branch from sessions s left join workspaces w on w.local_id = s.workspace_id where s.id in (...)`. `Thread.displayName` is, in priority order: the custom name (see Renaming), then the Conductor name: `workspace_name` when `user_set_workspace_name = 1` and it is non empty, else `pr_title` when non empty, else `branch`; then the newest run's title; then `session.workspaceName`. `Thread.description` is `sessions.title` when non empty, else the newest active run's title. Without a DB row the name is the newest run's title (so several threads from one workspace no longer all read the workspace name) and the description is the run title.

State, first match wins:
- `error`: DB status `error`
- `working`: DB status `working`
- `waiting_on_you`: a wait is pending, or DB status `waiting`
- `idle`: alive
- `dead`: otherwise

## CLI: `bin/mc` (`#!/usr/bin/env bun`, symlinked to `~/.claude/bin/mc`)

- `mc serve`: start the server in the foreground. `mc open`: start the server if it is not answering (the same detached start as `mc push`, logging to `$MC_HOME/server.log`), wait until it answers, then run `open http://localhost:<port>` (port from `PORT`, default 4747).
- `mc push <file|->`: create or update a run from agent JSON. Input has `runId`, `skill`, `title`, optional `summary` (one sentence on what the thread is about, shown on the Overview; the newest run with a summary wins), optional `overview` (markdown-lite text explaining the PR's problem and change for a reader new to the code, shown on the Overview; the newest run with an overview wins), `agents`, `todos` (todo fields: `id`, `kind` (`decision`, `question`, `approval` or `finding`), `kind`, `category`, `title`, `question`, `recommendation`, `options`, `positions`, `tradeoffs`, `caveats`, `evidence`, `links`, `diffs`; missing arrays (including `diffs`, a list of `{ path, patch }` unified diff hunks) default to `[]`, missing `recommendation` to `null`). Optional `session`; when absent fill from env: `conductorSessionId` = `CONDUCTOR_SESSION_ID`, `workspacePath` = `CONDUCTOR_WORKSPACE_PATH` (fallback cwd), `workspaceName` = basename of path, `repo` = basename of parent dir, `branch` = `git -C <path> branch --show-current`, `pr` = null. Merge rule for an existing run: agent fields overwrite; for todos with an existing id keep `state`, `answer`, `submittedAt`, `pickedUpAt`, `resolution`; new todos start `open`; todos missing from input are kept. Sets `updatedAt`, `status: 'active'`. Prints the run file path.
  - Finding todos (`kind: 'finding'`, for review style runs): always `category: 'needs-you'`, never options, recommendation or preset answers (the split guard ignores them). They add optional `severity` (breaking, regression, worth-knowing, dead-code, refactor), `verification` (how it was confirmed), `draftComment` (an inline review comment in Thinh's voice) and `suggestedQuestions` (2 to 4 short follow ups). `question` is the plain language explanation, `evidence` / `links` carry the location and the PR permalink, `positions` (optional) what each reviewer said, `alsoRaisedAs` (optional list of ids of other items that name the same root cause), and `diffs` / `conversation` work as for decisions.
  - Run `mode` (`build`, `review` or `self-check`) and optional `pr` (`{ number, url, author }`) are kept across pushes. Without a `mode` the run is `review` when its skill is `prod-ready-check` and `build` otherwise.
  - Pre-answered key decisions: a new todo with `category: 'key-decision'` and a `recommendation.optionId` starts as `answered` with `answer { optionId: recommendation.optionId, text: '', deferred: false, answeredAt: now, preset: true }`. The UI shows the violet council icon, the user can change the answer (saving clears `preset`), and it counts toward Submit like any answer. `mc wait` and prompt lines append ` (council pick)` after the chosen label for preset answers. Guard (applied on every push, `categoryOf` in `src/store.ts`, rule in `src/council.ts`): a todo may only be `key-decision` when it has at least 2 positions, every position has the same `optionId`, and that `optionId` equals the recommendation's. Otherwise it is forced to `needs-you` and never gets a preset answer. A todo that is already `answered` with a preset answer and becomes a split on a later push goes back to `open` with `answer: null`; an answer Thinh gave himself is kept. Covered by `src/store.test.ts`.
  - Autostart: after writing, if `GET http://127.0.0.1:${PORT||4747}/api/threads` does not answer within 500ms, spawn `bun <repo>/src/server.ts` detached (stdio appended to `$MC_HOME/server.log`, `.unref()`), passing `MC_HOME` and `PORT` through, so the server survives the agent being killed.
  - Notifications: when the push added todo ids that did not exist before and start `open`, run `osascript -e 'display notification "<n> new todos: <run title>" with title "Mission Control" subtitle "<workspaceName>"'` and, if `~/.claude/skills/ping/scripts/slack-notify.sh` exists and `ROCKY_OAUTH_TOKEN` is set, `slack-notify.sh "Mission Control: <n> new todos in <workspaceName> (<run title>) http://localhost:<port>"`. Both are fire and forget and never fail the push. Both are skipped when `MC_NO_NOTIFY=1`. The osascript notification is also skipped when the app reported itself focused within the last 30s (`GET /api/presence`, asked with a 500ms timeout; no server or no answer counts as not focused). The Slack ping is unaffected.
- `mc wait <runId> [--timeout <minutes>, default 240]`: blocks until the run has todos with `state: 'submitted'` or a submitted, undelivered question (see below). Watch the file (`fs.watch` plus a 1s poll fallback). If such todos already exist, return immediately. On release: set those todos to `picked_up` with `pickedUpAt` (a question todo, see below, goes back to `open` instead), write, then print to stdout and exit 0:
  ```
  MISSION CONTROL DECISIONS <runId>
  - D1 <title>: <chosen option label | "answered">. Note: <text or "none">
  - D4 <title>: QUESTION from Thinh: <text>. Reply with mc reply <runId> D4 "<answer>"; the decision stays open.
  - D5 <title>: QUESTION from Thinh (unanswered): <text> Reply with mc reply <runId> D5 "<answer>".   (printed once, when a question was delivered through Submit; a pending question that was not submitted never releases `mc wait`, and the copy prompt text lists every pending question)
  - Any line that appends a period after free text (QUESTION, POST COMMENT) only adds it when the text does not already end in `.`, `!` or `?`.
  ...
  Still open: D3, D4   (or "Still open: none")
  Next: act on the decisions, run `mc resolve <runId> <todoId> "<what you did>"` for each, then `mc wait <runId>` again if anything is still open.
  ```
  On timeout print `TIMEOUT <runId>` and exit 2.
- `mc reply <runId> <todoId> "<text>" [--question "<new question text>"]`: append `{ from: 'agent', text, at }` to the todo's `conversation` and clear `pending` on the earlier Thinh messages (the todo stays open); `--question` also replaces the todo's `question`. The server's reply endpoint uses the same store function.
- `mc resolve <runId> <todoId> [text]`: state `done`, `resolution` = text, `doneAt` = now (`Todo.doneAt` is optional; older todos without it are never counted as done today). A finding whose answer is a comment (`answer.comment: true`) becomes state `commented` (not `done`) with the resolution as the comment URL; it is then locked.
- `mc done <runId>`: run `status: 'done'`.
- `mc prompt <sessionId>`: print the copy prompt for a thread (same text as the UI button).
- `mc step "<text>" [--agent <agentId>] [--session <id>]`: record the agent's current step in `$MC_HOME/steps/<sessionId>.json` as `{ current: { text, at, agent } | null, history: [{ text, at, agent }] }` (atomic, under a lock; the last 30 history entries are kept and the new step is appended to them; session from `CONDUCTOR_SESSION_ID` unless `--session` is given; the old `{ text, at }` shape reads as the current step with no agent). `mc step --clear` clears `current` only. `Thread.step` is `current` and `Thread.steps` is the history; the server watches the steps directory like the runs directory. A step without an agent belongs to the thread's orchestrator.
- `mc avatars`: download any missing avatar icons into `$MC_HOME/avatars/` (see Avatars).

## HTTP API

- `GET /` the app.
- `GET /api/threads?archived=0|1` → `Thread[]` (`archived=1` includes archived threads, sorted after the active ones).
- `POST /api/threads/:sessionId/archive` and `/unarchive` → add or remove the session id in `archived.json`, broadcast, return `{ ok }`.
- `POST /api/threads/:sessionId/name` body `{ name: string | null }` → sets or (when empty or null) resets the custom name in `names.json`, broadcasts, returns `{ ok }`. 404 for an unknown thread.
- `GET /api/events?archived=0|1` SSE; event `threads` with the full `Thread[]` JSON on every change (run dir change via `fs.watch`, or live state change). Send a comment ping every 15s.
- `POST /api/runs/:runId/todos/:todoId/answer` body `{ optionId: string|null, text: string, deferred: boolean, question?: boolean }` → state `answered`, sets `answer` with `answeredAt` (and `question: true` for an "Ask the agent" answer). Rejected (409) when state is `submitted`, `picked_up` or `done`.
- `POST /api/runs/:runId/todos/:todoId/ask` body `{ text }` → appends `{ from: 'thinh', text, at, pending: true }` to the todo's `conversation` without touching state, answer or submission. 400 on empty text, 404 for an unknown todo. `POST .../reply` body `{ text }` → appends `{ from: 'agent', text, at }` and clears `pending` on the earlier Thinh messages (same 400 / 404). When the session has not polled within 60s (`instantAsk` false), the server answers the question itself, see "Fallback answerer" below.
- `GET /api/sessions/:sessionId/work` → `{ questions, submitted, sync }`, polled by the agent session's Claude Code mod. `questions` has one entry per todo of that session's runs whose latest Thinh message is pending, with `{ runId, todoId, title, question, text, recommendation, options (id, label), positions (agent, optionId, summary), tradeoffs, caveats, conversation }`. `submitted` lists runs with todos in state `submitted` as `{ runId, todoIds, waitActive }`, where `waitActive` is true while an `mc wait <runId>` / `mc.ts wait <runId>` process is running (the same ps check as the live state). Every call records a heartbeat (`lastModPollAt[sessionId] = now`, at request start and again when it responds); `Thread.instantAsk` is true when the session polled within the last 60s. `sync` is `{ requestedAt }` while a sync from chat is requested and not acknowledged, else `null`; the long poll releases as soon as a sync is requested (and returns at once while one is pending, so the mod must ack).
- `POST /api/threads/:sessionId/sync` → stores `syncRequestedAt` for the session (in memory and in `$MC_HOME/sync.json`, `{ [sessionId]: iso }`, written atomically under a lock), broadcasts, returns `{ ok, requestedAt, mod }` where `mod` says the session polled within the last 60s. 404 for an unknown thread. `POST /api/sessions/:sessionId/sync/ack` clears it (always 200) and broadcasts. `Thread.syncRequestedAt` carries the pending value.
- `POST /api/runs/:runId/todos/:todoId/dismiss` → `dismissed` (kept for compatibility; nothing in the UI calls it, and stored `dismissed` todos render read only). `POST .../reopen` → `open`, `answer: null` (only from `answered` or `dismissed`).
- Finding actions, all rejected (409) once the todo is locked: `POST .../understood` → state `understood`, `POST .../drop` → state `dropped` (both local only, no agent involved, both set `doneAt` and are reversible through `reopen`), and `POST .../comment` body `{ text }` → state `answered` with `answer { optionId: null, text, deferred: false, answeredAt, comment: true }`, which counts toward Submit like any answer (400 on empty text). In `mc wait` and prompt text it reads `- F2 <title>: POST COMMENT at <first evidence ref> (<first link, if any>): <comment text>. After posting, run mc resolve <runId> F2 "<comment url>".` `reopen` also works from `understood` and `dropped` and clears `doneAt`.
- `GET /api/presence` → `{ focused }`, true when the client reported focus within the last 30s. `POST /api/presence` body `{ focused: boolean }` records it.
- `GET /avatars/:id.png` → a downloaded avatar icon (see Avatars).
- `POST /api/focus-conductor` → runs `open -a Conductor`, returns `{ ok }` (no UI uses it).
- `POST /api/threads/:sessionId/submit` → for every run in the thread, todos in `answered` become `submitted` with `submittedAt`; append a submission `{ id, at, todoIds }` to each touched run. Returns `{ submitted: number }`. Returns `{ submitted, submissionIds }`. Pending questions that are deliverable (see "Fallback answerer") are submitted too: their latest Thinh message gets `submittedAt`, the submission lists them in `questionTodoIds`, and the response is `{ submitted, questions, submissionIds }`.
- `POST /api/threads/:sessionId/unsubmit` body `{ submissionId }` → moves that submission's todos that are still `submitted` back to `answered` (clearing `submittedAt`) and removes the submission; todos already `picked_up` stay. Returns `{ reverted, pickedUp }`. It also clears `submittedAt` on questions of that submission that were not delivered yet (counted in `reverted`); delivered ones count as picked up.
- `GET /api/threads/:sessionId/prompt` → `{ text }`. Text: for each run with answered or submitted todos, a header `Mission Control decisions for <title> (run <runId>)`, the same bullet lines as `mc wait`, and `Still open: ...`.

Text `#ececef`, soft `#cfd0d6`, muted `#9a9ba4`, dim `#80818b`. Accents: primary amber `#f0a43a` (hover `#f7b75a`, text on amber `#1a1206`), violet `#a78bfa` for council picks, green `#4cc276`, blue `#6b9bff`, red `#f85149`. Accent tints use the `--<color>-rgb` triplets so a palette change is one block of variables. ### Modes

Every thread is in one of three modes, always visible: `build` (/avengers implementation runs, decisions), `review` (/prod-ready-check on someone else's PR: findings for the author, draft comments) and `self-check` (/prod-ready-check on Thinh's own PR: will it break CI or prod, a fix list with no draft comments). `Thread.mode` is the newest run's mode (`build` for a steps-only thread) and `Thread.pr` that run's `pr`.

- Sidebar row: a 14px line icon before the name and nothing else: hammer for build, magnifying glass for review, shield for self-check (tooltips "Build", "Review of someone else's PR", "Pre-merge check of your PR"), each in its own tint.
- Overview, Decision and Finding headers: a small mode label next to the title with the same icon and the word ("Build", "Review", "Pre-merge check"; amber, blue, green), plus for review and self-check the PR number and author when known (`#12 by octo`, a link to the PR).
- The right pane section label follows the mode: build "Needs you", review "To review", self-check "To fix". In a self-check thread a finding has no comment box and no Post comment button, only Got it and Drop.

### Middle: Overview and Decision

Two tabs at the top left of the middle pane: "Overview" and "Decision". Selecting a thread opens Overview; clicking a todo (or `j` / `k`) switches to Decision; Overview is one click (or `o`) away. When no todo is available Overview is shown, never an empty "Select a todo." state. Decision only reacts to answer keys while it is the visible tab.

Overview is analytics, quiet and glanceable, CSS only (no chart library), one screen at 1920x1000 without scrolling:

A thread whose todos include findings shows these tiles instead of or next to the decision tiles (only when each kind exists): To review, Understood, Comments queued (answered, submitted or picked up), Commented, Dropped, and a findings bar with the same states.

- Runs: a small legend above the list (needs you, answered, council pick, sent, done), then one compact row per run: skill chip, title, one 14px rounded block per todo (wrapping when needed), `done/total`, active/done, relative updatedAt. Block colors: open is transparent with a 1.5px amber outline, answered by Thinh amber, answered as a council pick (preset) violet, submitted or picked_up blue, done green, dismissed the row border grey. Each block has the tooltip `<id> · <title> · <state>` and clicking it opens that todo in the Decision view (switching the right pane tab when the todo is not in the current one).

## prc-to-mc

`bin/prc-to-mc.ts <prod-ready-check context dir> [summary]` prints a push input for a prod-ready-check run (`src/prc.ts`, pure, covered by `src/prc.test.ts`). Every agreed and every contested item of the latest tally becomes a `finding` todo (contested first, dropped items skipped): `question` is the plain explanation built from the failure and the fix, `severity` and `verification` (the item's evidence text) are copied, `evidence` holds the location, `links` the pull request, `caveats` notes low confidence, `draftComment` is empty and `suggestedQuestions` is `[]` (the skill fills those), and every finding, agreed or contested, carries the three seats' final positions (`{ agent, stance, summary: "<stance> · <severity>", reason, evidence }`, no option ids). `alsoRaisedAs` lists the ids of the other tally items linked to this one: a seat's reason saying "same root" or "same root cause as <ids>" links both items to each other, ids not in the tally and self references are ignored, and the list is ordered Claude (`C`), Codex (`X`), Grok (`G`) then by number; it is omitted when empty. The `summary` argument is kept. When `<context dir>/overview.md` exists its trimmed text is pushed as `overview`. Git ref prefixes (a leading `pr-<n>:` or `origin/<branch>:` before a path) are stripped from every location and evidence ref (the location, the verification text and each reviewer's evidence). The run id is built from `meta.json`'s `url` (`https://github.com/team-plain/services/pull/11506` gives `prc-services-11506`), falling back to the directory layout (resolved to an absolute path) only when the url is missing. `severity` is the consensus of the seats' final positions: the most common `severity` among `agree` and `revise` stances, ties broken by the owner's original label.

The run also gets `mode` and `pr`: `mode` is `self-check` when `meta.json`'s `author.login` equals Thinh's GitHub login (`gh api user --jq .login`, run once with `GH_TOKEN` removed; any failure falls back to `review`; `MC_GH_LOGIN` overrides the lookup for tests) and `review` otherwise, and `pr` is `{ number, url, author }` from `meta.json`.

When the context dir has a `diff.patch`, each todo gets `diffs` from `extractDiffs` (`src/diffs.ts`, pure, covered by `src/diffs.test.ts` with `bun test`): for every `path` or `path:line` in the item's `location` it takes that file's hunks from the patch, only the hunk containing the line when a line is given, else all hunks, at most 3 per file.

## Fallback answerer

`src/fallbackAsk.ts`. When a question arrives through the ask endpoint and the session has not polled the work endpoint within 60s, the server runs an answerer chain (`answerQuestion`) in the thread's `session.workspacePath`; `MC_FALLBACK_CMD` replaces the `claude` executable (tests point it at a fake script and never run the real one). One chain runs per question at a time, and none is ever spawned for a session with `instantAsk` true. Each stage first tags the pending message with `answerer` (`session` or `notes`) so the UI can say what is happening.

1. Session copy (`answerer: 'session'`), only when the Conductor DB has a row for the session id (`hasConductorSession` in `src/live.ts`): `~/.local/bin/claude -p --resume <sessionId> --fork-session --no-session-persistence --tools "" --model sonnet "<prompt>"`, 60s timeout. The Conductor session id is the Claude session id, so this reads a forked copy of the chat and never touches the live session. The prompt is `askPrompt` (decision title, the question, the two sentence / under 40 words instruction, the decision context JSON). Output is clamped to two sentences and 60 words.
2. Notes reviewer (`answerer: 'notes'`), when stage 1 failed or there is no session row: `~/.local/bin/claude -p --model sonnet --tools "Read,Grep,Glob,Bash" --allowedTools "Read" "Grep" "Glob" "Bash(git show:*)" "Bash(git log:*)" "Bash(cat:*)" "Bash(jq:*)" --no-session-persistence "<prompt>"`, 120s timeout. The prompt (`notesPrompt`) says Thinh is reviewing the finding or decision `<id> "<title>"` of the run title and asks the question, then tells the model it is a read only reviewer, points it at the run's `contextDir` notes (`report.md`, `mc.json`, `debate/`, `diff.patch`, `external/`; that sentence is dropped without a `contextDir`), tells it to read code only with `git show pr-<N>:<path>` or `git show origin/<base>:<path>`, and asks for at most three short plain sentences, answer first, no headings or lists. Earlier messages of the conversation follow as "Conversation so far". Output is clamped to three sentences and 90 words.
3. Both failed: the message is marked `fallbackFailed` (also immediately when the session has no workspace path).

An answer is posted through the reply store function, only while that question is still the pending one. `POST /api/runs/:runId/todos/:todoId/retry` (409 when nothing is pending, the question was already submitted or a chain is still running) clears `fallbackFailed` and `answerer`, sets the message time to now and runs the chain again.

Runs have an optional `contextDir` (absolute path of the skill's notes dir). `bin/prc-to-mc.ts` sets it to the resolved context dir, push parsing keeps it and a later push without it keeps the stored one.

Typing indicator text per path: "Asking the agent…" (the mod, `instantAsk`), "Asking a copy of the session…" (stage 1), "Looking it up with this review's notes… (about 30s)" (stage 2). After the patience time (`questionPatienceMs` in `src/prompt.ts`: 45s for the mod, 75s for `session`, 150s for `notes`) or on `fallbackFailed` the indicator goes away. Then, on a thread that is not dead, a muted "No quick answer yet, the agent will see it with your next Submit" (stale, not failed) or "Couldn't get an answer, Retry, or the agent will see it with your next Submit" (failed). On a dead thread (no live session, so no Submit button, the footer offers Copy prompt) it reads "Couldn't get an answer, Retry" and never mentions Submit.

Questions are deliverable by one rule shared by the line, the Submit label and the server (`isDeliverableQuestion`): a pending, not yet submitted Thinh question is deliverable once `fallbackFailed` is set or its patience time passed. The Submit button counts them (a dead thread shows no Submit button and counts none). Submit then delivers them: the message gets `submittedAt`, `mc wait` releases when a submitted, undelivered question exists, prints the QUESTION line and marks the message `deliveredAt` so it is never printed twice. The question stays pending until the agent replies.

## Reviewer Consensus

The Finding view's "Reviewers" section (`web/Consensus.tsx`, wording in `web/reviewerText.ts`, covered by `web/reviewerText.test.ts`) replaces the old per reviewer list. It shows one consensus sentence: "Agreed by Claude and Grok; Codex refined the fix" when nobody rejects, "Codex holds it; Claude and Grok reject it" when a seat disagreed or withdrew, "Rejected by ..." when nobody holds it. Under it each seat is a pill with its avatar, name and stance word (agreed, refined the fix, disagreed, withdrew; green or red border for agree or disagree). A "Show reasoning" link, collapsed by default and reset per finding, expands each seat's reason and evidence refs.

`bin/backfill-positions.ts <context dir> <runId>` reads the latest tally of that context dir and, under the run lock and without touching `updatedAt`, sets `positions` and `alsoRaisedAs` on the existing run's todos matched by id (todos with no tally item are left alone, nothing else changes).

## Sync From Chat

Thinh often settles decisions in the Conductor chat, which leaves the run stale. "Sync from chat" is in the thread context menu (after Rename), in the Cmd+K palette and as a small text link on the Overview header. It POSTs `/api/threads/:sessionId/sync`. When the response says `mod: true` the mod turns the request into a prompt for the session (the request waits in `work.sync` until the mod acks) and a toast reads "Sync requested". Otherwise the client cancels the request with an ack, copies the prompt from `src/syncPrompt.ts` (`syncPrompt(runIds)`: the shared `SYNC_PROMPT`, then a blank line and `Runs: <run ids>`) and toasts "Sync prompt copied, paste it into the Conductor chat". While a request is pending and no run of the thread changed since it (`isSyncing` in `src/sync.ts`), a muted "Syncing…" sits next to the live state on the Overview header. Covered by `src/sync.test.ts` (spawns a server on a random port) and `src/syncPrompt.test.ts`.
